## 0. 一句话结论

**并发安全不是「小心」出来的 —— 它取决于「判断」有没有落在原子操作里。**

防超卖的实现只有一件事：把「够不够」塞进一条 SQL 的 `WHERE` 里，让数据库**一次原子完成**；
再靠 `rowcount` 判断"到底改到没改到"。

---

## 1. 概念：什么是「超卖」，为什么会发生

### 超卖

库存 **5** 件，实际卖出 **10** 件。

### 原因：TOCTOU / check-then-act

**生活比喻：只有 5 个名额的报名表。**
10 个人**同时**看表 → 每人都看到"还剩 5 个，我能报" → **10 个人都报了名**。

问题不在"检查"，而在**检查与动作之间那段时间差**。

| 术语 | 含义 |
|---|---|
| `check-then-act` | 先检查、再动作（两步之间有缝） |
| `TOCTOU` | Time-Of-Check to Time-Of-Use（检查时刻 → 使用时刻，中间有窗口） |

## 2. 项目里的实现（三个要点）

```464:477:sut/store.py
            # ★ 防超卖的关键：单条 SQL 条件更新，天然原子；靠 rowcount 判定成功与否。
            #   绝不能写成「先 SELECT stock 再 UPDATE」——那是 check-then-act 竞态。
            cursor = conn.execute(
                "UPDATE products SET stock = stock - ?, updated_at = ?"
                " WHERE id = ? AND stock >= ?",
                (quantity, now, row["product_id"], quantity),
            )
            if cursor.rowcount != 1:
                # 抛错会触发事务回滚，此前已扣减的库存全部还原
                raise errors.Conflict(
                    "库存不足，下单失败",
                    code="INSUFFICIENT_STOCK",
                    detail={"product_id": row["product_id"], "requested": quantity},
                )
```

| 要点 | 为什么必须这样 |
|---|---|
| 判断写在 `WHERE` 里 | 原子性由数据库保证，不留"查完再改"的缝 |
| 靠 `rowcount` 判定 | ★ `UPDATE` **不报错 ≠ 改到了**：条件不满足时它影响 **0 行**（静默） |
| 抛错 → 事务回滚 | 一张单多件商品时，**前面扣掉的库存要能全部还原**（同一 `with db.transaction()` 内） |

## 4. ★ 实测 B：原理对照实验（本课最有价值的部分）

在**同一个临时 SQLite 库、同一个并发压力**下，对比两种写法：

```
❌ 先查再减（check-then-act）
   初始库存 = 5   并发线程 = 10
   卖出（返回 success） = 10   ← 期望 5
   最终库存(落库)      = -5   ← 期望 0
   → ★ 超卖 5 件（这正是要演示的：错误写法真的会超卖）

✅ 条件更新（UPDATE ... WHERE stock >= ?）
   初始库存 = 5   并发线程 = 10
   卖出（返回 success） = 5    ← 期望 5
   最终库存(落库)      = 0    ← 期望 0
   → 正确：卖出数不超过库存
```

**意义**：把「为什么不能那样写」从**经验之谈**变成**可复现的实证**。
对照组里 `time.sleep(0.005)` 模拟"读到之后、写回之前"的耗时（真实代码里在做校验/打折/写日志）。

### ⚠️ 一个更隐蔽的变体

若错误写法是 `UPDATE stock = <刚读到的值 - 1>`（写**绝对值**），结果是
「**卖出 10 件、库存却显示 4**」—— **账实不符，而库存数字看起来还挺正常**。
这比"库存变负数"**更难发现**。

## 5. ★★★ 诚实口径（面试必背，`test_07_concurrency.py:5-13` 原文）

> 这两个测试**【不能】**说成「证明了数据库级防超卖 / 证明了并发正确性」。
> **SQLite 是单写者模型，写入本身被串行化，因此测不出 MVCC 数据库（MySQL InnoDB / PG）下的竞争表现。**
>
> 它们真正证明的是：**并发访问下不崩** —— 无死锁、无 `database is locked`、无 5xx，且**计数守恒**。
> 「防超卖由单条原子条件更新保证」是【**设计保证**】，不是靠这两个测试证明的；
> 测试只是把它在并发路径上验证了一遍。

**为什么这句话重要**：面试官里只要有一个懂并发，夸大其辞就会被打穿；
而主动划清"证明了什么 / 没证明什么"，反而显得诚实且懂边界。

## 9. 自测题 + 标准答案

**Q1. 用生活场景解释 TOCTOU：为什么"先查再减"会超卖？**
A：像"只有 5 个名额的报名表"，10 个人同时看都看到"还剩 5 个"→ 都报名。
问题在**检查与动作之间的时间差**（check-then-act）。实测复现：卖出 10 件、库存 -5。

**Q2. 为什么正确写法要看 `rowcount`？`UPDATE` 没报错难道不等于改成功了吗？**
A：**不等于**。`UPDATE ... WHERE stock >= ?` 在条件不满足时**影响 0 行且不报错**（静默）。
所以必须用 `cursor.rowcount != 1` 判定"到底有没有扣到"（`store.py:471`）。

**Q3. 为什么"一个订单多件商品"时事务回滚是必须的？**
A：因为前几件商品可能已经扣减成功，第 N 件失败时若只报错不回滚，**前面扣掉的库存会永久丢失**。
代码用 `with db.transaction()` + `raise` 触发整体回滚（`store.py:447`、`:473-477`）。

**Q4. 我们的并发测试证明了什么、没证明什么？**
A：**证明**：并发访问下不崩（无死锁、无 `database is locked`、无 5xx）+ 计数守恒。
**没证明**：MVCC 数据库（MySQL/PG）下的竞争表现 —— SQLite 单写者模型，写入本身被串行化。
「防超卖由单条原子条件更新保证」是**设计保证**，测试只是验证了一遍。（`test_07_concurrency.py:5-13`）

## 10. 附：做这个演示工具时踩的 3 个坑（真实记录）

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | `SyntaxError: invalid syntax` | 字符串里嵌了**被规范化为 ASCII 的引号**，把字符串截断 | 内层改用 `「」` |
| 2 | 脚本 `exit code = 1` 但结果其实正确 | **对照组的"超卖"是预期结果**，却按"失败"判定了 | 给对照组单独设 `should_oversell=True` |
| 3 | `KeyError: 'id'`（建商品失败） | **商品名写死 `"抢购商品"`**，第二次运行撞重名 —— **违反了本项目"靠造数不靠 reset"的原则** | 改用 `utils.data.unique()` 加 uuid 后缀 |

> 第 3 条特别值得记：**项目自己的原则（uuid 造数）不是形式主义** —— 一旦违背，第二次运行就会失败。
> 修完后连跑两次，结果一致、`exit code = 0`。
